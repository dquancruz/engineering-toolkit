# Checklist: code review

When to use it: before approving a pull request. Go through the common part and the one for the kind of change.

## Every PR <!-- section: common -->

- [ ] The description says what changes and why
- [ ] The diff only includes what the description explains
- [ ] There are no secrets, personal data or files generated by mistake
- [ ] Errors are handled and their messages help to understand the failure
- [ ] Names and style follow the project conventions
- [ ] CI is green

## Feature <!-- section: feature -->

- [ ] The new behavior meets the acceptance criteria
- [ ] There are tests for the normal case, the edges and the errors
- [ ] API or data changes are compatible or have a migration plan
- [ ] The usage documentation is up to date
- [ ] It can be observed in production (logs, metrics) and turned off if needed

## Bugfix <!-- section: bugfix -->

- [ ] The cause is explained, not only the symptom
- [ ] There is a test that fails without the change and passes with it
- [ ] Other places with the same mistake were looked for
- [ ] The change is the smallest one needed

## Refactor <!-- section: refactor -->

- [ ] Observable behavior does not change
- [ ] Existing tests pass unmodified
- [ ] No functional changes are mixed in
- [ ] The result is simpler than before

## Documentation <!-- section: docs -->

- [ ] Commands and examples were run
- [ ] Links and paths exist
- [ ] Each important fact has a source
- [ ] It does not duplicate another document

## Dependencies or configuration <!-- section: dependencies -->

- [ ] It says why something is added or updated
- [ ] The breaking changes of the new version were read
- [ ] The lockfile changes consistently
- [ ] The vulnerability audit does not get worse
- [ ] The license is acceptable
- [ ] Configuration changes have safe defaults

## For a prompt <!-- prompt -->

What `engkit prompt --checklist code-review` adds to the prompt.

### Limits <!-- limits -->

- Give the file and line of every finding
- Separate blocking defects from suggestions

### Verification <!-- verify -->

- The PR description matches the diff (`git diff`)
- It states what could not be verified

### Feature <!-- variant: feature -->

#### Limits <!-- limits -->

- Do not approve API changes without compatibility or a migration plan

#### Verification <!-- verify -->

- There are tests for the new behavior, its edges and errors

### Bugfix <!-- variant: bugfix -->

#### Limits <!-- limits -->

- Do not accept changes that are not needed to fix the defect

#### Verification <!-- verify -->

- The defect test fails without the change and passes with it

### Refactor <!-- variant: refactor -->

#### Limits <!-- limits -->

- Do not accept changes to observable behavior

#### Verification <!-- verify -->

- Existing tests pass unmodified (`npm test` or the project command)

### Documentation <!-- variant: docs -->

#### Limits <!-- limits -->

- Do not approve facts without a source

#### Verification <!-- verify -->

- The example commands run and the links open

### Dependencies or configuration <!-- variant: dependencies -->

#### Limits <!-- limits -->

- Do not add dependencies without justifying them

#### Verification <!-- verify -->

- The audit reports no new vulnerabilities (`npm audit` or the project command)
